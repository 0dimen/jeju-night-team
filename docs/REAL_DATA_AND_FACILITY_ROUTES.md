2026년 11월 19일 작업. 이 문서 하나로 "무엇을 받았고, 무엇을 바꿨고, 어떻게 다시 만들고, 무엇이 남았는지"를 확인할 수 있게 정리했습니다.

- CCTV 포함 목적을 생활방범 1종에서 **생활방범·교통단속·어린이보호·시설물관리 4종**으로 넓혔습니다. 표현은 ‘방범 CCTV’가 아니라 ‘공공 CCTV’입니다.

## 2단계: 다시 만드는 순서

결과 파일도 저장소에 들어 있으므로 확인만 하려면 실행할 필요가 없습니다. 값을 바꿔 다시 계산할 때 저장소 루트에서 실행합니다. 추가 설치는 필요 없습니다(표준 라이브러리 + 기본 의존성).

```bash
.venv/bin/python scripts/build_facility_routes.py                          # 최단·시설 선호 경로 (오프라인)
.venv/bin/python scripts/build_facility_routes.py --cctv-source standard   # 행안부 표준 CCTV로 계산 (오프라인)
.venv/bin/python scripts/fix_light_axes.py                                 # 가로등 원본을 바꿨을 때: 복구 사본 다시 생성
.venv/bin/python scripts/collect_foot_routes.py                            # 구간을 바꿨을 때: OSRM 경로 수집 (온라인)
.venv/bin/python scripts/build_facility_routes.py --download-osm           # 구간을 바꿨을 때: osm 파일을 지운 뒤 도로망 다시 받기 (온라인)
```

| 산출물 (`data/open/` 아래) | 만든 스크립트 |
|---|---|
| `derived/jeju_city_streetlights_20241010_axisfixed.csv`, `.note.json` | fix_light_axes |
| `foot_routes/*_route_candidates.geojson`, `*_osrm_responses.json`, `collection_summary.json` | collect_foot_routes |
| `osm/*_overpass.json` | build_facility_routes `--download-osm` |
| `facility_routes/*_facility_routes_{datahub,standard}.geojson`, `summary_*.json` | build_facility_routes |

- `collect_foot_routes.py`의 요청 캐시는 `data/raw/osrm_cache/`(Git 제외)에 남습니다. 캐시가 없는 컴퓨터에서 실행하면 외부 서버에 다시 요청하고, 지도 자료가 그사이 바뀌었으면 결과가 달라질 수 있습니다.
- 온라인 요청은 공개 지점 2구간에 한정됩니다(Nominatim 검색 4건, OSRM 경로 4건 이상, Overpass 도로망 2건). 초당 1회 이하·식별 가능한 User-Agent를 적용했습니다. **개인 위치를 이 스크립트에 넣지 마세요.** 외부 서버가 요청 위치를 기록할 수 있고, 결과가 저장소에 올라갑니다.

## 가로등 축 교환 복구

- 문제 행 16,155개는 모두 위도 칸과 경도 칸의 값이 서로 바뀐 형태였습니다. 파일 안에서 두 덩어리로 연속해 있고 읍면 단위로 통째로 바뀌어 있습니다: 조천읍 5,661 · 구좌읍 4,848 · 한림읍 4,232 · 우도면 770 · 추자면 641 · 한경면 3.

- 복구 사본에는 `좌표수정` 열이 추가되고 바꾼 행에 `위도경도교환`이 표시됩니다. `facility_cleanup.prepare_facilities` 기준 사용 가능 행이 35,864 → 52,014로 늘어납니다. 남은 5행은 종류 미기재입니다.
- `facility_cleanup`은 여전히 자동 교환을 하지 않습니다. 복구는 사람이 결정해 따로 실행하는 단계로 분리했습니다.
- 시연 구간인 연동은 2,212행 모두 정상이라 복구 전후 결과가 같습니다.

## CCTV 목적 범위 변경

결정과 근거는 [CCTV 선택 근거](CCTV_SELECTION_DECISION.md) 맨 위에 적었습니다. 요약:

| 자료 | 전체 | 생활방범만(v1) | 4개 목적(v2) |
|---|---:|---:|---:|
| 제주데이터허브 846 | 479 | 8 | 473 |
| 행정안전부 표준(제주분) | 1,043 | 71 (전부 서귀포시) | 937 |

- 방범 CCTV 전체 목록은 공개 자료에서 찾지 못했습니다. 통합관제센터는 약 1만 8천~1만 9천 대를 관제한다고 보도되어 있어, 공개 목록은 일부입니다. 전체 위치는 제주도 담당 부서에 정보공개청구나 협조 요청이 필요합니다.
- 행정안전부 표준 파일에서 제주시는 교통단속 362행뿐이고, 서귀포시는 시설물관리 504행이 가장 많습니다. 두 시의 자료 성격이 달라 **두 구간의 CCTV 비율을 서로 비교하면 안 됩니다.**
- `scripts/build_facility_routes.py --cctv-source standard`는 표준 파일의 열 이름만 바꿔 같은 설정으로 고릅니다. 기본값은 설정의 출처와 같은 `datahub`입니다. 어느 쪽을 기준 자료로 삼을지는 아직 정하지 않았습니다.

## 경로의 종류 — 혼동 주의

| 이름 | 무엇인가 | 어디서 나오나 |
|---|---|---|
| OSRM 기본 경로 (R1) | 지도 서비스가 준 최단 도보 경로 | `collect_foot_routes.py` |
| OSRM 경유 경로 (R2) | 가로등 한 곳을 억지로 거치게 한 **임의 우회로**. 시설이 많은 길이 아님 | `collect_foot_routes.py` |
| 최단 경로 (SHORTEST) | 우리 계산부가 OSM 도로망에서 직접 찾은 최단 경로 | `build_facility_routes.py` |
| 시설 선호 경로 (FACILITY) | 가로등·공공 CCTV와 가까운 구간의 비용을 낮춰 찾은 경로 | `build_facility_routes.py` |

앱이 제안하려는 ‘기존 최적 경로 대 시설이 많은 경로’ 비교에 해당하는 것은 아래 두 줄(SHORTEST·FACILITY)입니다. R2를 안전 경로처럼 설명하면 안 됩니다.

## 시설 선호 경로 계산 방식

- 도로망: OpenStreetMap에서 구간 주변 약 600m를 받아, OSRM 보행 프로필과 같은 도로 종류만 사용합니다(자동차 전용·출입 제한 제외).
- 도로 조각마다 "가로등 반경 15m 안에 드는 길이 비율", "공공 CCTV 반경 50m 안에 드는 길이 비율"을 계산합니다. 길이 계산은 기존 `agent/geometry.covered_length`를 그대로 씁니다.
- 비용 = 길이 × (1 + 가로등 가중치 × (1 − 가로등 비율) + CCTV 가중치 × (1 − CCTV 비율)). 가중치 기본값은 각각 1입니다.
- 결과가 최단 거리의 1.5배를 넘으면 가중치를 절반씩 줄여 다시 찾습니다.
- 반경·가중치·우회 한도는 모두 **임시 연구값**이며 명령 옵션으로 바꿀 수 있습니다. 근거가 있는 값이 아닙니다.

### 결과 (2026-11-19, 기본값)

| 구간 | 최단 | 시설 선호 | 가로등 15m | 공공 CCTV 50m |
|---|---|---|---|---|
| 삼무공원~누웨마루거리 | 352.4m · 4.7분 | **최단과 같은 길** | 60.3% | 13.6% |
| 중앙로62번길~매일올레시장 | 307.6m · 4.1분 | **최단과 같은 길** | 62.3% | 36.9% (표준 자료로는 70.2%) |

- **두 시연 구간에서는 기본 가중치로 두 경로가 같게 나옵니다.** 300m 안팎의 도심 구간이라 최단 경로가 이미 시설 인접 비율도 가장 좋은 편입니다.
- 연동은 가중치를 4로 올리면 다른 길이 나옵니다: 470m(+33%), 공공 CCTV 13.6% → 47%, 가로등 60% → 65%. 서귀포는 가중치 8까지 올려도 같습니다.
- 같은 도로망에서 무작위 출발·도착 150쌍으로 확인하면(표준 CCTV 자료, 가중치 1) 경로가 달라지는 비율은 직선 250~450m에서 약 30%, 600~1,000m에서 약 60%입니다. 달라질 때 평균적으로 거리는 3~5% 늘고 가로등 비율은 5~10%p, CCTV 비율은 10~16%p 높아집니다. 즉 계산부는 동작하지만 **지금의 짧은 시연 구간이 차이를 보여 주기에 적합하지 않습니다.**
- 우리 최단 경로(352.4m·307.6m)가 OSRM 기본 경로(338.3m·298.0m)보다 조금 깁니다. 출발·도착점을 가장 가까운 도로 교차점에 붙이기 때문입니다(OSRM은 도로 중간 지점에 붙임). 붙인 거리는 연동 0.1m·15.0m, 서귀포 16.8m·6.3m입니다.

### 가로등 반경에 대해

OSRM 경로 4개로 반경을 바꿔 본 결과입니다.

| 반경 | 5m | 10m | 15m | 30m |
|---|---|---|---|---|
| 네 경로의 가로등 인접 비율 | 9~13% | 32~43% | 59~67% | 89~96% |

- 30m는 모든 경로가 높게, 5m는 모든 경로가 낮게 나와 둘 다 경로를 구분하지 못합니다.
- 경로 선은 도로 중심선이고 가로등은 길가에 있어, 5m는 도로 폭과 좌표 오차만으로도 넘습니다. 그래서 15m를 임시 기본값으로 두었습니다.
- ‘100m당 가로등 수’나 ‘가로등 사이 가장 긴 공백’ 같은 지표가 더 나을 수 있으나 아직 계산하지 않았습니다.

## 하지 않은 것과 한계

- 기본 에이전트·`/routes/compare`·`/demo` 화면에는 연결하지 않았습니다. 산출 GeoJSON은 기존 `load_routes` 검사는 통과하지만 `rights_confirmed: false`라 `FileRouteEngine`의 실제 자료 게이트는 통과하지 않습니다.
- 시설 위치는 밝기·점등·작동·촬영 범위를 뜻하지 않습니다. 인접 비율은 안전 확률이 아닙니다.
- 범죄·사고 자료가 없어 "시설이 많은 길이 더 안전하다"는 근거는 없습니다.
- 인도·횡단보도·계단 여부를 반영하지 않습니다. 현장 확인도 하지 않았습니다.
- 출발·도착을 도로 중간 지점에 붙이지 않고 가장 가까운 교차점에 붙입니다.
- 서귀포 구간의 OSRM 수치(298.0m·407.0m)는 [기존 수집 기록](REAL_ROUTE_COLLECTION.md)의 479.4m·700.3m와 다릅니다. 기존 수집의 정확한 지점이 문서에 없어 지명 검색 결과를 그대로 썼기 때문입니다. 연동 기본 경로는 338.3m로 일치합니다.
- `docs/CCTV_SELECTION_DECISION.md`가 안내하는 `scripts/prepare_selected_cctv.py`와 `data/processed/cctv_selection_check.json`은 이 공유 저장소에 없습니다.
